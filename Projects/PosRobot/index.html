PosRobot

A production-grade multi-process control server that bridges HMIs to Boston Dynamics Spot robots over a custom binary protocol — with dual-channel safety architecture and database-driven fleet management.

Python 3.10 Multiprocessing Boston Dynamics SDK 3.3 SQL Server Custom Binary Protocol OpenCV TCP/IP E-Stop Safety

01 The Problem

Controlling an industrial robot from a remote HMI (Human-Machine Interface) over TCP/IP is not just a networking problem — it's a safety-critical systems engineering problem. If the command channel hangs or the controlling process crashes, the robot must stop. Not eventually — immediately.

The Python Boston Dynamics Spot SDK runs complex gRPC-based communication internally. Early prototyping revealed that Spot SDK objects cannot be pickled — they can't be shared across multiprocessing.Process boundaries using the standard high-level APIs. This meant the initial shared-memory design (Robot instances in a shared dict across processes) would not work with real hardware.

The solution: Each Spot instance lives in exactly one process. All other processes communicate with it through dedicated TCP sockets and shared-memory flags — not Python object sharing.

02 Process Architecture

The system uses a process-per-connection model with strict separation of safety (E-Stop) and command channels.

04 Safety Architecture

This is where the project diverges from hobbyist robot controllers. The safety design follows industrial automation patterns:

Dual-Channel Isolation

E-Stop and Command run in separate multiprocessing.Process instances on separate TCP ports. A crash in the command process cannot affect the E-Stop channel.

Heartbeat Watchdog

HMI sends heartbeat (code 11000) continuously. If no header arrives within the socket timeout (3 seconds), settle_then_cut() is called automatically — the robot sits down and cuts motor power.

Lease Management

Spot SDK's lease system prevents multiple controllers. LeaseKeepAlive with return_at_exit=True ensures the lease is returned even on unexpected process termination.

Login Mutual Exclusion

Only one HMI can control a robot at a time. The _logged_in_hmi_ip flag prevents duplicate login (error 10001/10002). The E-Stop port also validates the connecting HMI's IP address.

Graceful Shutdown Sequence

# Ctrl+C triggers cascading shutdown:
Ctrl+C
  ├─► stop_all.value = 1
  ├─► log_queue.put(None)      → logger_process exits
  ├─► status_queue.put(None)   → status_queue_process exits
  └─► server_thread.join()    → tcp_server closes sockets
       └─► hmi_connection   → socket.close()
            └─► Spot.__del__()  → lease returned, E-Stop settled

06 Database-Driven Fleet Management

Robot configuration is not hardcoded. At startup, the server queries the Robots table and dynamically instantiates robot objects. Adding a new robot to the fleet is a database operation — no code changes, no restart.

08 Lessons Learned

Pickle Isn't Always the Answer

The original design shared Spot instances via multiprocessing.Manager dict. Online testing revealed Spot SDK objects (wrapping gRPC channels) can't be pickled. This forced a full redesign to process-per-connection with pipe/socket communication — which turned out to be better for safety isolation anyway. The "limitation" became the architecture's strongest feature.

Industrial Protocols Are Worth the Effort

Building a custom binary protocol may seem like reinventing the wheel when REST exists, but for real-time robot control, the deterministic 19-byte header with packed structs provides predictability that JSON-over-HTTP cannot match. Plus, the JSON-defined telegram schema makes it configurable without recompilation.

No-Robot Mode Is Essential

The No_Robot flag — tested first, hardware second — allowed HMI development to proceed in parallel with robot integration. Every command path returns correct mock responses, making the HMI team unblocked without a Spot on every desk.
