PosRobot

HMI와 Boston Dynamics Spot 로봇을 잇는 멀티프로세스 제어 서버 — 커스텀 바이너리 프로토콜, 이중 안전채널 아키텍처, DB 기반 플릿 관리.

Python 3.10 Multiprocessing BD Spot SDK 3.3 커스텀 바이너리 프로토콜 SQL Server OpenCV E-Stop 안전설계

해결 과제

산업용 로봇을 원격 제어하는 것은 단순한 네트워킹 문제가 아닌 안전이 중요한 시스템 엔지니어링 문제입니다. 초기 프로토타입에서 Spot SDK의 gRPC 객체가 pickle이 불가능하다는 것을 발견했고, 이로 인해 초기 shared-memory 멀티프로세스 설계가 무산되었습니다. 결국 프로세스 격리와 소켓 통신 기반으로 아키텍처를 완전히 재설계했습니다.

프로세스 아키텍처

각 HMI 연결은 독립된 프로세스로 실행됩니다. 안전채널(E-Stop)과 명령채널은 별도 프로세스에서 별도 TCP 포트로 분리되어 — 한쪽이 죽어도 다른 쪽에 영향을 주지 않습니다.

# 프로세스 트리 (로봇 1대, HMI 1개 연결)
main()
  ├── logger_process        ← Queue → 로그 디스크 기록
  ├── status_queue         ← Queue → 텔레메트리 → SQL Server
  └── tcp_server :50000    HMI 연결 수락
        └── hmi_connection    인증 + 로봇 할당
              └── Spot.login()
                    ├── estop()      E-Stop 채널 (전용 포트)
                    │     └► 3초 내 하트비트 없으면 → settle_then_cut()
                    └── hmi()        명령 채널 (전용 포트)
                          └► command_control()
                                ├► MotionHandler → Spot (gRPC)
                                ├► CameraHandler → Spot CAM
                                └► LightHandler  → LightingClient

안전 설계

이중 채널 격리

E-Stop과 명령은 별도 포트/프로세스에서 실행. 명령 채널 충돌 ≠ 안전 손상.

하트비트 감시

HMI가 지속적으로 하트비트(코드 11000) 전송. 3초 타임아웃 시 자동 settle_then_cut().

리스(Lease) 관리

Spot SDK 리스 + return_at_exit=True — 크래시 발생해도 리스 반환 보장.

상호 배제

로봇당 하나의 HMI만 연결. IP 검증 로그인으로 중복 제어 방지 (에러 10001/10002).

핵심 인사이트

Pickle 제약 → 더 나은 설계

최초 shared-memory 설계는 Spot SDK 객체가 pickle 불가능해 실패. 소켓 통신 기반 프로세스-per-커넥션으로 재설계한 것이 아키텍처의 가장 강력한 안전 기능이 되었습니다.

No-Robot 모드로 개발 병행

No_Robot 플래그가 모든 명령에 mock 성공을 반환 — Spot 로봇 없이도 HMI 개발을 병행할 수 있었습니다.
