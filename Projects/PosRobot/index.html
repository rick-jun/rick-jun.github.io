PosRobot

Multi-process control server bridging HMIs to Boston Dynamics Spot robots via a custom binary protocol — with dual-channel safety architecture and database-driven fleet management.

Python 3.10 Multiprocessing BD Spot SDK 3.3 Custom Binary Protocol SQL Server OpenCV E-Stop Safety

The Challenge

Controlling an industrial robot remotely is a safety-critical systems problem — not just networking. Early prototyping revealed that Spot SDK's gRPC objects cannot be pickled, breaking the initial shared-memory multi-process design. The architecture had to be redesigned around process isolation and socket communication.

Process Architecture

Each HMI connection gets its own process. Safety (E-Stop) and command channels are isolated in separate processes on separate TCP ports — a crash in one cannot affect the other.

Safety Design

Dual-Channel Isolation

E-Stop and Command are separate processes on separate ports. Command crash ≠ safety compromise.

Heartbeat Watchdog

HMI sends heartbeat (code 11000) continuously. 3-second timeout triggers automatic settle_then_cut().

Lease Management

Spot SDK lease with return_at_exit=True — lease is always returned, even on crash.

Mutual Exclusion

Only one HMI per robot. IP-validated login prevents duplicate control (errors 10001/10002).

Key Insights

Pickle Limitation → Better Design

The original shared-memory design failed because Spot SDK objects can't be pickled. The forced redesign to process-per-connection with socket communication became the architecture's strongest safety feature.

No-Robot Mode Unblocked Development

The No_Robot flag returns mock success for every command — HMI development proceeded in parallel without a Spot robot on every desk.
